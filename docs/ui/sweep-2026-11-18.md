### Notes, not counted as defects

- P7 (portal filters lost on the way to sign-in) doesn't happen as reported. For a visitor without a session cookie, src/proxy.ts already keeps the address and its filters in `next`. The page's own redirect never runs, because the signed-in shell redirects first. What remains is rarer: with a stale session cookie (revoked or expired), SignedInShell sends any `/app` page to sign-in with `next=/app`. Fixing that would mean forwarding the path in a request header on every request. Agreed with 9c to leave it (low).
- `/sign-up` and `/help/contact` log 8 console errors each from the Turnstile iframe: the CSP blocks its `data:` connect test, and a sandboxed `about:blank` frame logs too. Worth one check that the widget passes in a real browser (37).
- The public top bar is a `div`, so the site has no banner landmark. The app bar is the same. Assigned to f7, with the one-shell change.
- The e2e build's header avatar sometimes came back with an absolute `http://localhost:3300/api/files/…` src (desktop account-contact photo, flaky). Not a product bug. next/image sets `src` again once mounted, to catch an error from before hydration, and that resolves it against the page's own address (never APP_URL). The spec now compares path and query, as the avatar's unit test already did.
- Anonymous visitors on the live site see no tasks or helpers, since the demo marketplace shows only to signed-in testers. So the public task and helper pages couldn't be checked signed out.
- 404 pages for addresses with a dot in them (`/wp-login.php`) never reach the app: src/proxy.ts skips them, and Next's plain 404 answers. That's intended, since it's cheap for bots.

  - No permission, IDOR or link-integrity problems.

  - Sign-up dedupe gives the same response for an existing email, and the signed cookie is safe.
